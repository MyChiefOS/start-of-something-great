# Operations log

Every action Claude takes on Day One Great's accounts or settings for Aaron, in the open. It covers changes outside the code itself: settings, workflow runs, branches, and anything on GitHub or Vercel that isn't a pull request. Code changes are already recorded by their pull requests and commits.

How each entry happens:
1. Claude proposes the action and how to undo it.
2. Aaron concurs in the conversation, and the entry records when.
3. Claude acts, then records the result.

Some things Claude never does, even when asked:
- create accounts
- type or handle passwords, keys, client secrets or tokens
- spend money
- accept terms of service

Those stay with Aaron. The log starts on October 15, 2026; earlier actions are in the pull requests and conversation history.


## Runbook: close the site now

If Release 2 must come off the public internet at once (a leak, abuse that the brake isn't holding, a legal demand), in this order; each step alone is enough, the next is the fallback if the one before can't be done.

1. **From GitHub (about 3 minutes, the normal way):** Actions, Production setup, Run workflow on `main`: steps `stage,redeploy`, stage `closed`. Approve the setup job. The run sets `LAUNCH_STAGE=closed`, redeploys, waits, and checks the live site reports `closed` before it says done. Every Release 2 route then answers as it did before the database existed; nothing is deleted.
2. **From Vercel, if GitHub is unavailable:** the project, Settings, Environment Variables: set `LAUNCH_STAGE` to `closed` (it is plain text). Then Deployments, the current Production deployment, Redeploy. Check https://dayonegreat.com/api/status shows `"stage": "closed"` (open it with `?now=1` added to skip the cache).
3. **If the database itself must be cut off** (a credential may have leaked): run Production setup with steps `database,redeploy` and rotate_db_password ticked. Every deployment built before it, rollbacks included, loses its database access. If GitHub is unavailable, reset the `dog_web` password in Supabase (Project Settings, Database); the site then fails closed until the next setup run.
4. **Never** close by rolling back to an older deployment: it keeps the stage it was built with (RISKS.md RK68).

Afterwards: record the time, the step used and the reason in the log below; the uptime monitor will raise an issue if the live stage no longer matches the last recorded one (EXPECTED_STAGE), which is expected after step 2 and is cleared by the next setup run.
