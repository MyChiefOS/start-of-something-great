## Runbook: close the site now

If Release 2 must come off the public internet at once (a leak, abuse that the brake isn't holding, a legal demand), in this order; each step alone is enough, the next is the fallback if the one before can't be done.

1. **By pull request (the close switch, control 7, R-10; since the go-live release the repository decides the stage):** Claude opens a PR that changes `launch.json` to `{ "stage": "closed", ... }`; Aaron merges it and Vercel's production deploy of the merge closes every Release 2 route (launch.js; test/preopen-safety.test.js). Check https://dayonegreat.com/api/status shows `"stage": "closed"` and `/api/ready` shows `"stage_repo": "closed"`. To reopen, a PR puts it back to `"public"` (Aaron's decision, as opening was). The uptime monitor compares the live stage with the repository's, so after this step it stays quiet. **A real close carries step 3a in the same PR** (the site's login off). `launch.json` closes the current deployment. Step 3a is what reaches every deployment: an Instant Rollback to a public build would serve it on dayonegreat.com itself, where the redirect doesn't apply; the redirect of generated addresses (from the go-live build on; builds before it are closed) is proven only by the check after the go-live merge; and `/api/cron`, which the redirect leaves out, still runs the timers on the database from a public build's own address (RISKS.md RK68). Reopening then needs db/emergency/reopen-site-login.sql as well.
2. **From Vercel (the immediate close; Aaron, in the dashboard):** the project, Settings, Environment Variables: set `LAUNCH_STAGE` to `closed` (plain text; any value but `public` closes, and it can never open the site). Then Deployments, the current Production deployment, Redeploy. Check https://dayonegreat.com/api/status shows `"stage": "closed"` (open it with `?now=1` added to skip the cache). This is hand work for Aaron, so step 1 comes first; the uptime monitor's "Go-live stage" check then reports that the live stage differs from the repository's (an alert only, expected), until step 1 records the close or the setting is removed.
3. **If the database itself must be cut off**, under route B:
   - 3a. **The site's login off** (the database side of control 7): Claude copies `db/emergency/close-site-login.sql` unchanged into `db/migrations` as the next number (for example `028_close_site_login.sql`), runs `node scripts/manifest.js` and `npm run db:snapshot` (no snapshot change is expected: roles aren't in it), and opens the PR; Aaron merges; the runner applies it. `dog_web` can no longer sign in and open `dog_web` connections are ended where the runner's login may end them (otherwise within 30 minutes); its password, membership and every table stay. Proof after: read-only `select rolcanlogin from pg_roles where rolname = 'dog_web'` is false, and `/api/ready`'s database probe fails (expected `error_28000`; through Supabase's pooler the code may differ: not yet seen). Undo: `db/emergency/reopen-site-login.sql` the same way. Tested on a throwaway database (test/preopen-safety.test.js); not yet run on Supabase.
   - 3b. **A credential may have leaked:** Claude opens a PR with a new migration that runs 022's block again (a new `dog_web` password, made inside the database) and a broker that refuses everyone (410); Aaron merges, and Claude deploys the broker from the merge. Don't use Supabase's "reset database password": it resets the main `postgres` login, not `dog_web`. Production setup no longer has a database step (R-14, the runner-alerts PR); it used to write a `DATABASE_URL` into Vercel, which would override the broker's and wouldn't match Vault.
4. **Never** close by rolling back to an older deployment: it keeps the stage its own commit's `launch.json` said, so a rollback across a stage change serves the old stage (RISKS.md RK68).
